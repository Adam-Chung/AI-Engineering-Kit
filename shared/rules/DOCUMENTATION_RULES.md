# Documentation Rules

Write documentation for its intended audience and purpose.

Include only information relevant to the document.

Verify technical claims against the available code, configuration, tests, or authoritative project sources.

Do not invent behavior, APIs, dependencies, examples, or future plans.

Clearly distinguish current behavior from proposed or planned behavior.

## Content

Include the relevant sections when they help the reader:

- Purpose and scope
- Prerequisites
- Architecture
- Workflow or data flow
- API or interface behavior
- Practical examples
- Common pitfalls and limitations
- Confirmed future improvements

Do not add empty or irrelevant sections merely to satisfy a template.

## Style

Use clear, concise language and consistent terminology.

Lead with what the reader needs to understand or accomplish.

Keep examples minimal, correct, and consistent with the documented behavior.

Use tables or diagrams only when they make relationships, workflows, or architecture materially easier to understand.

Avoid exposing secrets, credentials, personal data, or unsafe operational details.

## Maintenance

Update related documentation when implementation or behavior changes.

Remove or clearly mark outdated information.

State uncertainty or missing information instead of guessing.
